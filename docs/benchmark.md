# 측정 기록

운영 환경 처리량이 아니라 **같은 장비에서 두 구현을 비교한 결과**입니다.

| 항목 | 값 |
|---|---|
| CPU / 메모리 | Intel i7-8750H (6C/12T) / 15.9 GiB |
| OS / JVM | Windows 11 / Amazon Corretto 21.0.11 |
| DB / 부하 생성기 | PostgreSQL 17.7 (Docker) / k6 2.2.0 (Docker) |
| 튜닝 | JVM 힙 · 웹 서버 스레드 · DB 커넥션 풀 기본값 |
| 방법 | 각 방식 3회 측정, 중앙값 사용. 회차마다 JVM 재기동 후 20건 워밍업 |

부하 생성기와 DB, 애플리케이션이 한 노트북의 자원을 공유합니다.

재고 1개로 예약을 만든 뒤 50 VU로 같은 주문에 결제 요청 100건 동시 전송

| 조건 | 완료 | 거절 | 예상 밖 응답 | 요청 p95 | 최종 상태 |
|---|---:|---:|---:|---:|---|
| 동일 멱등성 키 100건 | 100 | 0 | 0 | 1,230 ms | 출금·결제·주문 확정 각 1회 |
| 서로 다른 키 100건 | 1 | 99 | 0 | 275 ms | 출금·결제·주문 확정 각 1회 |

<details><summary>테스트로 발견한 경쟁 조건</summary>

서로 다른 키로 같은 주문을 결제한 최초 실행에서 1건 성공 · 84건 거절 · **15건이 예상 밖의 400**이었습니다. 늦게 도착한 요청이 이미 확정된 예약을 보고 실패하면서, DB에 있는 기존 결제를 확인하지 못한 것이 원인이었습니다.

기존 결제를 외부 주문 API 호출 전과 결제 불가 판정 직전에 다시 확인하도록 순서를 바꾼 뒤, 같은 조건에서 1건 성공 · 99건 거절로 일관되게 처리됐습니다.

</details>

## 4. 재고 선점 쿼리 실행 계획

재고 100만 행 중 90만 개가 판매된 상태에서 다음 한 건을 선점하는 쿼리입니다.

```sql
SELECT * FROM product_stock
WHERE product_id = ? AND status = 'AVAILABLE'
ORDER BY id ASC LIMIT 1 FOR UPDATE SKIP LOCKED
```

| 항목 | `(product_id, status)` | 부분 인덱스 |
|---|---:|---:|
| 실행 시간 | 131 ms | **0.39 ms** |
| 읽은 블록 | 9,965 | **9** |
| 필터로 버린 행 | 900,000 | **0** |
| 사용된 인덱스 | `product_stock_pkey` | `idx_product_stock_claim` |

기존 인덱스에는 `id`가 없어 `ORDER BY id`를 만족하지 못합니다. 옵티마이저는 대신 PK를 id 순으로 스캔하며 조건에 맞는 첫 행을 찾았고, 판매된 90만 행을 전부 버렸습니다.

```sql
CREATE INDEX idx_product_stock_claim
    ON product_stock(product_id, id)
    WHERE status = 'AVAILABLE';
```

`id`를 인덱스에 포함해 정렬을 없애고, 조건을 부분 인덱스로 옮겨 판매된 행을 인덱스에서 제외했습니다. **재고가 소진될수록 인덱스가 작아집니다.**

<details><summary>같이 확인한 것</summary>

- 완전 소진된 상품은 인덱스에 항목이 없어 **0.04 ms**에 빈 결과를 반환합니다. 기존 인덱스로는 100만 행을 스캔했습니다.
- 게이트가 0.5초마다 호출하는 재고 개수 조회(`count(*)`)는 이 인덱스로 개선되지 않습니다. 100만 행을 세는 비용이라 별도 문제입니다(약 45 ms).
- `FOR UPDATE`는 실제 행을 잠그므로 Index Only Scan이 되지 않습니다. 위 수치는 실제 쿼리 형태로 측정했습니다.

원문은 [`load-test/explain/`](../load-test/explain)에 있습니다.

</details>

## 한계

- 절대 처리량을 운영 용량으로 해석하지 않습니다. 부하 생성기와 DB가 같은 장비에 있습니다.
- 2,000 RPS 탐색에서는 부하 생성기 쪽 한계에 먼저 걸려 요청을 다 보내지 못했습니다. 이 환경의 상한은 2만 건 접수입니다.
- 확인한 것은 초과 판매 방지, 락 대기 감소, 주문 서버 유입 제한입니다.
- 실행 스크립트와 k6 원자료(JSON)는 [`load-test/`](../load-test)에 있습니다.
